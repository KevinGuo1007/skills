# 与 Matt Pocock 技能协作

选择协作技能时读取。本技能维护批次闭环；Matt 技能处理具体阶段。推荐配合，独立执行也可，不自动安装依赖。

## 先核实实际能力与调用方式

从当前会话技能列表和相应 `SKILL.md` 核实名称、职责、前置及默认副作用。以下是参考角色映射，不是运行时保证存在的名称，也不要求每批都走一遍。

| 阶段 / 角色 | Matt 仓库中的参考技能 | 本批交接内容 |
| --- | --- | --- |
| 需求澄清 | `grill-with-docs`、`grilling`、`domain-modeling` | 目标、尚未解决的产品决定、已有术语/架构约束 |
| 规格与任务拆分 | `to-spec`、`to-tickets` | 仅新需求需要；已有批准规格和任务直接复用 |
| 单项或整批实施 | `implement`、`implement-spec` | 批次记录、批准版本、范围、依赖、验证计划和动作授权 |
| 测试驱动 | `tdd` | 已确认测试接缝、行为和必要验证范围 |
| 难定位缺陷 | `diagnosing-bugs` | 实际失败证据、复现条件、稳定问题标识及累计尝试 |
| 标准与规格审查 | `code-review` | 固定比较范围、批准规格/原任务和本批脏树内容 |
| 便携交接 | `handoff` | 指向持久批次记录、原始证据和唯一下一步 |

Matt 的 [调用约定](https://github.com/mattpocock/skills/blob/main/.agents/invocation.md)区分用户显式调用和模型可调用技能。2026-11-02 核查时的例子：

- `grill-with-docs`、`to-spec`、`to-tickets`、`implement`、`implement-spec`、`handoff` 为用户显式调用，只能建议用户运行，不由本技能自动调用。
- `grilling`、`domain-modeling`、`tdd`、`diagnosing-bugs`、`code-review` 可由模型在适用时选用。

以当前安装版本为准，尊重其调用限制。用户专用技能需要衔接时，保存记录，给出明确调用建议与输入；若用户选择由本流程独立完成该阶段，则自行完成已授权工作，如实记录未使用相应技能。

## 衔接契约

**进入阶段前**：提供原任务/规格、批次记录、批准版本、目标工作目录及差异边界、必要验证和允许动作。阶段产物返回原真源，批次只记录引用、结果与下一步。

**返回闭环时**：核对实际改动、验证证据、构建/源码身份、未执行项、失败尝试及保存状态。子技能完成一张卡，不自动代表整个 Feature 或依赖卡已验收。

**遇到限制时**：缺技能、子代理、设备或集成工具时，记录实际执行方式和覆盖缺口。能以等价方式满足当前验收就继续；缺必要能力则仅阻塞对应项。不要虚构已调用技能、独立审查或真实环境验收。

## 需要特别核对的默认行为

- `implement` 的参考实现包含审查后的自动提交；`implement-spec` 包含分支/工作树、并行子代理、集成及 PR 等动作。用户应了解这些默认动作；复用技能不扩大当前批次授权。必要时在明确授权内使用，或选择独立实施。
- 测试接缝确认复用已有决定。没有确认的新接缝按相应技能处理；不把所有视觉和探索性工作强行改成 TDD。
- 检查实施技能的完整回归要求是否与本批验证计划一致；调用前解决冲突，不偷偷跳过必要检查，也不额外制造逐卡完整回归规则。
- `code-review` 参考实现使用 Standards / Spec 两个独立子代理。调用时保留其方式；无法执行时报告限制，并区分自行检查与独立双轴审查。
- `handoff` 的临时文档作为索引，活动批次仍保存在项目持久位置。换会话不重置问题计数、批准或验收事实。
