# Feature Development Loop

以可独立验收的交付单元推进软件项目。Feature 是可观察的用户或使用方结果，可由多张任务卡、多个模块或仓库交付；重构和基础设施改动也可按相同闭环执行。

## 1. 恢复现场，建立项目适配

优先找到项目当前批次的入口和原记录，再读相关原任务、规格、设计及仓库约定。没有活动批次才规划新候选；已完成记录原地保留。

首次使用或项目条件变化时，读 [项目适配指南](references/project-adaptation.md)，确定记录位置、真源、验证渠道、环境与执行边界。适配是当前批次中的简短约定，无需建立配置框架或自动调度器。

- 批次记录使用项目已有位置；无约定时采用 `docs/features/<batch-id>.md`，由 `docs/features/README.md` 链接当前记录。入口只路由，任务状态继续留在原 tracker。
- 核对工作目录、分支、HEAD、既有差异及未跟踪文件，区分本批内容与用户已有修改。涉及运行环境时，对账当前部署和配置。
- 核对计划与批准版本、验收证据的日期和适用范围、未完成动作及稳定问题标识下的累计尝试。聊天摘要只辅助定位，不能代替原记录。
- 活动记录已有执行者时，先确认接管或分工。多人写入共享记录前重读；同一环境的有副作用动作由一个明确执行者串行处理。

恢复完成时说明：已实现、已验证、待验收和已完成分别有哪些，当前阻塞是什么，以及唯一下一步和停止条件。事实冲突或缺失保持未知，不推断为批准或通过。

推荐与 Matt Pocock 技能配合。选择协作技能前读 [协作指南](references/matt-pocock.md)，核实实际可用版本及调用限制；缺失时按本流程独立执行。

## 2. 选择一个可验收批次

优先推进目标关键路径，复用已有规格、任务及实现。选择能独立操作和验证的适中范围，写清目标、排除项、关联原任务、依赖闭包、选择理由及主要不确定性。

依赖闭包包括外部服务、数据、设计或人工决定等前置。它们不必全在本批实现，但必须明确是否已就绪、由谁负责以及会阻塞哪一项。任务可按依赖逐项认领，无需把所有任务同时启动。

## 3. 形成可审阅计划并核实授权

新批次基于 [批次模板](assets/feature-batch.md) 建立记录；短批次合并不适用段落，保留阶段、计划/批准版本、授权来源、验收矩阵、证据、失败记录及唯一下一步。

计划至少明确：

- 当前源码与既有修改边界、实现模块、步骤、预计产物和风险。
- 行为到规格、任务及适用设计/契约的映射。设计可以是文字、现有产品或设计稿；接口记录实际标识及版本，未知项标为缺失。
- 验收矩阵：每项的必要性、前置和操作、可观察预期、验证渠道及证据方式。必要项不能靠标注“不适用”或“稍后”绕过。
- 针对性检查、扩大回归触发条件、必要完整回归节点及证据复用条件。
- 需要的工具、环境、账号/数据、人工参与，以及有副作用动作的授权范围。适用时列明环境保留与临时资源清理方案。

复用 Matt 规格或原任务中的计划和明确批准，不另写一份重复规格。现有授权明确覆盖当前计划就继续；授权不明时展示具体计划，停在 `awaiting-approval`。批准工作流或旧批次不等于批准新批次。

进入 `active` 前：`Approved revision` 与 `Plan revision` 一致，批准来源确实覆盖该版本，必要映射和验收明确，开发前置与相应动作授权就绪。恢复时版本不一致，回到规划或计划待审阶段。独立实施不依赖的后续联调前置可以列为验证阶段阻塞，先完成已授权的独立动作。

范围、业务规则或验收标准实质变化时升计划版本并重新确认；普通实现调整及范围内缺陷修复沿已有授权推进。

## 4. 实施与分层验证

逐项实施，记录边界和当前步骤。已有合适测试接缝时，在业务逻辑、转换和状态等路径采用 TDD；视觉或探索性工作选择适用验证方式。需要重新决定接缝时先确认，不为流程机械增加测试。

每次改动先运行能验证影响的最小有效检查。公共模块、契约或关键集成变化时扩大回归；按计划在集成节点完成必要的完整检查，无需逐卡重复整套。

按验收矩阵验证实际交付物：

- 本地检查先独立进行，未部署服务只阻塞对应集成项。
- 有真实服务交互要求时，用计划指定的真实目标和正常访问路径验证关键成功、错误及一致性；mock、健康探针或管理通道不能替代这项证据。
- 有 UI 时运行普通应用或页面，覆盖本批相关的完整操作、导航及关键加载/空/错误等状态。测试宿主、合成场景和普通运行分别记录。
- 库、CLI、后端、移动端和基础设施分别选择适用渠道；不强制 Figma、浏览器、模拟器或真机。人工/设备验收仅在批准矩阵要求时成为完成关口。

发现问题后定位、修复、重验受影响路径，保留失败记录。范围内修复自主继续；新的产品决定或超出授权的动作先解决对应缺口。

## 5. 审查与适用人工验收

审查范围实现及仓库标准，提供批准计划/原任务和固定比较基线。覆盖本批未提交和未跟踪内容，排除既有无关修改；仅审 `HEAD` 不能代表脏工作树中的交付物。使用审查技能时遵守其实际执行方式；没有相应技能时完成等价检查并如实记录审查方式。

修复审查问题后重验受影响项。所有必要机器可执行验收及审查通过后：

- 需要人工验收：转 `awaiting-acceptance`，提供最终产物/构建身份、运行条件、步骤和可观察预期，等待明确结果；失败回 `active`。
- 不需要人工验收：直接核对收口条件。

人工通过只覆盖被验收的产物。后续变更重新验证受影响项，必要时重新确认最终交付物；不能把旧构建结论写为新构建通过。

## 6. 收口并提出下一批

`completed` 必须同时满足：批准范围实现、全部必要验收和审查通过、适用人工结果明确、原任务及必要维护记录同步、证据与遗留项可追溯。必要验收未知、未执行或阻塞时保持未完成。

按计划清理临时资源并验证保留能力。提交、合并、推送、部署等操作沿当前项目授权执行，分别记录实际保存状态和交付状态；功能完成不推导生产放行。需要保留的分支、工作树或资源注明原因、责任人和后续处理条件。

保存原记录并更新入口，给出下一批建议。新批次从规划开始，不能继承上一批的范围批准。

## 状态与恢复协议

`Status` 使用以下值。仅在 `blocked` / `failed` 时用 `Resume stage` 保存被中断阶段；解除后回到该阶段并核实进入条件，再将此字段清为 `none`，其余状态也填 `none`。

| Status | 语义及转换条件 |
| --- | --- |
| `planning` | 整理候选、计划及缺口，计划可审阅后送审。 |
| `awaiting-approval` | 缺当前计划的有效批准；已具备且授权覆盖时进入 `active`。 |
| `active` | 在批准范围内实施和修复；必要机器验收与审查通过后进入适用验收或收口。 |
| `awaiting-acceptance` | 等待矩阵要求的最终人工结论；通过后收口，失败回 `active`。 |
| `completed` | 所有必要完成条件满足，记录已同步。 |
| `blocked` | 必要动作因缺资料、决定、工具、权限、环境或状态冲突无法安全推进；记录受影响项、原阶段、解除条件。只读查证等解除动作可在此状态执行，未知远程结果未对账前保持此状态。 |
| `failed` | 同一问题达到失败停止阈值，或出现需立即停止的异常；等待人工决定后恢复。 |

阻塞不影响无关且已授权的动作，须明确它们的下一步；所有可行动作都无法继续时保存记录并报告，不空转重试。

每次阶段转换、重要验证、失败尝试、人工决定和中断前，更新同一记录的时间/时区、执行者、恢复点、唯一下一步及停止条件。

## 证据与停止规则

- 每项验证绑定源码/产物、相关配置与契约、环境、时间、命令或操作、实际结果及原始证据位置。干净提交可用提交身份；脏树还需涵盖本批已跟踪和未跟踪内容的可重建快照或内容散列清单。仅有 HEAD 或文件名不足以识别未提交内容。
- 证据只有在相关源码、配置、契约、环境和适用范围仍一致时才能复用。已修复路径必须重验；通过、失败、未执行、阻塞、不适用分别记账，不适用说明理由。
- 用稳定问题标识跨会话累计连续失败修复尝试，默认第三次仍失败转 `failed`。已有更严格限制优先；记录每次原因、改动、结果及证据，无变更重跑也留痕，不靠换名、换会话重置。缺环境等前置转阻塞，不盲试。
- 远程动作结果未知时先对账，确认实际状态后才决定是否重试；出现意外数据损坏、越出授权或持续扩大影响的异常立即停止相关动作并报告。
- 授权绑定动作、资源、环境及适用的执行者、费用和期限；仍有效就复用。并行实施仅在已授权且边界独立时采用，共享环境写入串行。范围之外的生产或破坏性动作另行处理。
- 记录保存脱敏结论和证据指针；凭据、敏感载荷及访问令牌留在原受控位置。区分本地写入、Git 跟踪、提交、远端保存及外部证据保存，避免把“写了记录”称为“已备份”。
